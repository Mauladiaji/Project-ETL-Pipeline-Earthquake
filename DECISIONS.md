# Design decisions

Every decision must come with a trade-off. If no downside can be named, the choice was not
understood well enough.

| No. | Date | Decision | Alternative | Why | Trade-off |
|---|---|---|---|---|---|
| 1 | 2026-11-08 | Develop locally first (Docker + PostgreSQL), deploy to GCP later | Build directly on GCP | Fast, free iteration; does not burn the 90-day trial credit | Code must stay portable between PostgreSQL and BigQuery (`MERGE` syntax differs) |
| 2 | 2026-11-08 | PostgreSQL in Docker Compose | Install PostgreSQL natively on the host | Infrastructure as code: identical database for anyone, one command to start, easy to reset | One more tool to learn; needs disk space for images |
| 3 | 2026-11-08 | `postgres:17-alpine` image | `postgres:17` (Debian-based) | Much smaller image, which matters on a machine with little free system disk | Alpine uses musl libc; rare compatibility quirks with some extensions |
| 4 | 2026-11-08 | Python 3.12.6 for the virtual environment | Python 3.14 (also installed) | All required libraries ship prebuilt wheels for 3.12; 3.14 often forces a source build that fails on Windows | Not on the newest release; will need a planned upgrade later |
| 5 | 2026-11-08 | `venv` from the standard library | `uv` or Poetry | No extra tooling to install or explain while learning the fundamentals | Slower installs; no lock file, so transitive dependencies are not fully pinned |
| 6 | 2026-11-08 | Exact version pins in `requirements.txt` | Unpinned or `>=` ranges | Reproducible installs; a library release cannot break the pipeline on its own | Updates are a manual, deliberate step |
| 7 | 2026-11-08 | Configuration via `.env` + `python-dotenv`, `.env.example` committed | Hard-coded values, or a committed config file | Same code runs in every environment; no secret ever reaches the repository | Two files to keep in sync when a new setting is added |
| 8 | 2026-11-08 | One module per pipeline step, named after the step | A single `pipeline.py` | Separation of concerns: each step is testable and explainable in isolation | More files to navigate for a small project |
| 9 | 2026-11-08 | Auto-increment surrogate ID as the primary key of the `earthquakes` table | A natural key built from BMKG fields (a single field or a composite) | Simple and always unique; independent of source data quality, so a revised field never changes a row's identity | An ID says nothing about *which* event a row is, so on its own it cannot detect duplicates. The idempotent `MERGE` still needs a match condition (e.g. a unique constraint on identifying fields) — **open question**, see NOTES.md |
| 10 | 2026-11-14 | Keep raw JSON responses (implemented in `land.py`) | Transform in memory, store clean rows only | Allows replay and backfill after a bug is fixed | Extra storage; needs a retention rule |
| 11 | 2026-11-14 | Extract functions receive `base_url` as an argument | `extract.py` calls `load_config()` itself | Testable with any URL; `.env` is read once in `main.py`; a broken config stops the run at the start; on Cloud Run (no `.env` file) no extract code has to change | One more parameter threaded through the call chain |
| 12 | 2026-11-14 | Retry only timeouts, connection errors, 5xx and non-JSON bodies: 3 attempts, 10 s timeout, 1 s / 2 s exponential backoff | Retry everything; fixed delay; 30 s timeout | BMKG answers in well under a second (a full run takes about 1 s), so 10 s is generous while capping the worst case at about 33 s per feed; backoff avoids hammering a struggling server | A slow but alive server can be cut off early; HTTP 429 is not retried yet (known gap) |
| 13 | 2026-11-14 | Every extract failure surfaces as `ExtractError` (4xx immediately, others after the retries) | Let `requests.HTTPError` escape for 4xx | Callers handle a single error type | The difference between "our request is wrong" and "the server is down" lives only in the message text |
| 14 | 2026-11-14 | Raw files are opened with mode `"x"` and never overwritten; no random suffix in file names | Mode `"w"`, or a `uuid` in the name | Raw data is immutable; an accidental double write fails loudly instead of passing silently | A crash mid-write can leave a partial file that blocks a retry within the same second (future: write to a temp file, then link) |
| 15 | 2026-11-14 | Raw layout `<raw_dir>/<feed>/<YYYY-MM-DD>/<HHMMSS>Z.json`, all times in UTC, date of *ingest* | Date-first layout; local time; event date | One folder per feed; the ingest time describes the pull, not the earthquake; UTC matches cloud servers and avoids date drift | Two pulls of the same feed within one second collide (by design) |
| 16 | 2026-11-14 | Store the parsed payload (`dict`) | Store the raw response text or bytes | Simple, and equal in content to what BMKG sent | Not byte-identical (whitespace, key order); keep the response text plus metadata if exact provenance is ever needed |
| 17 | 2026-11-14 | `RAW_DATA_DIR` is resolved against the repo root unless it is absolute | Use the value as written (relative to the working directory) | Data lands in the same place wherever the program is started, e.g. by a scheduler | A relative value in `.env` means "relative to the repo", not to the shell; absolute paths are used as given |
| 18 | 2026-11-14 | `Config` is a frozen dataclass and the password is excluded from its `repr` | Plain dict or mutable object | Settings cannot change mid-run; printing or logging the config cannot leak the password | Still reachable as `cfg.postgres_password`; it must never be logged explicitly |
| 19 | 2026-11-14 | Logging to the console and to a file, UTC timestamps, level from `.env` | Console only; local time | A scheduled run leaves a trace; one time standard across logs and files | The log file grows without rotation (future: rotating handler); plain text rather than JSON |
| 20 | 2026-11-14 | Feeds are independent: a failing feed does not stop the others, and the exit code is 1 if any failed | Stop at the first failure | BMKG keeps no history, so data not fetched now can be lost for good, and the scheduler is still told that something failed | A partial failure can go unnoticed if nobody reads the log or the exit code |
| 21 | 2026-11-15 | Windows Task Scheduler, hourly, as a temporary local scheduler | No scheduling until the cloud deploy; manual runs | Snapshots are needed now to decide the business key and BMKG keeps no history; setup is cheap and Cloud Scheduler replaces it later | The laptop must be on; gaps appear when it is off |
| 22 | *(pending)* | Business key used in the `MERGE ... ON` clause | Fuzzy matching; hash key; composite natural key | To be decided from about a week of snapshots: which fields BMKG actually revises | See NOTES.md: the surrogate ID alone cannot match incoming rows |
| 23 | *(planned)* | `MERGE` (upsert) into the target table | Append everything, deduplicate in a view | Target table is always clean and query-ready | `MERGE` scans the target; needs partitioning at scale |
| 24 | 2026-11-15 | Hourly schedule (running through Task Scheduler for now) | Every minute | Respects the source's fair use; M5.0+ events are not that frequent | Up to one hour of latency |
| 25 | 2026-11-15 | `validate_record` returns a list of rejection reasons (empty list = valid) | Return `True`/`False`; raise at the first failed rule | The quarantine table needs the reasons, and one record can break several rules at once | Every rule runs for every record, a little more work than stopping at the first failure |
| 26 | 2026-11-15 | Validation only checks values and never changes them (`"10 km"` stays text) | Convert and validate in one step | Each step has one job: validate asks "readable and plausible?", transform does the conversion | Numbers are parsed twice (here and again in `transform`) |
| 27 | 2026-11-15 | Only `DateTime`, `Coordinates`, `Magnitude`, `Kedalaman` are required | Require every field | Optional fields (e.g. `Wilayah`, extra fields in the felt-earthquake feed) can be empty without making the event useless; rejecting on them throws away good data | A record with an empty optional field is accepted, so those columns need to allow NULL downstream |
| 28 | 2026-11-15 | Bounding box lat -15..15, lon 90..150, chosen from observed data (lat -9.2..5.59, lon 95.72..141.9) plus a wide margin | Exact outline of Indonesia; global range (-90..90, -180..180); no check | BMKG also reports offshore events; a tight box would quarantine real events, a global range would not catch garbage coordinates | A wrong coordinate that still falls inside the box passes; the box must be revisited if BMKG widens its coverage |
| 29 | 2026-11-15 | Magnitude 0..10, depth >= 0 with no upper cap; `nan` and `inf` are rejected explicitly | Tighter ranges; trust `float()` | Wide, simple ranges avoid false rejects; `nan` passes every comparison silently, so it must be caught on purpose | An absurd depth (say 5000 km) would pass; add a cap if it ever appears in the data |
| 30 | 2026-11-15 | A timestamp may be at most 5 minutes in the future | Zero tolerance | The clocks of BMKG and the pipeline machine differ slightly; zero tolerance would quarantine valid events | A wrong timestamp up to 5 minutes ahead is accepted |
| 31 | 2026-11-15 | Event time comes from `DateTime` (ISO 8601, UTC); `Tanggal`/`Jam` (Indonesian date text, WIB) and `Lintang`/`Bujur` are ignored in favour of `Coordinates` | Parse `Tanggal` + `Jam` and convert WIB to UTC | The source already provides standard formats; parsing month names (`Okt`, `Agu`) and zones adds code and failure modes for no gain | The pipeline depends on BMKG keeping `DateTime` and `Coordinates` stable; a change fails loudly in `validate` or `transform` |
| 32 | 2026-11-15 | Missing or blank optional text becomes `None` (NULL later), with spaces stripped | Keep whatever BMKG sends (`""`, spaces, missing) | One single form of "empty" avoids `WHERE x = ''` versus `IS NULL` mismatches and invisible-space groups | The difference between "BMKG sent nothing" and "BMKG sent an empty string" is lost |
| 33 | 2026-11-15 | `transform_record` is a pure function and receives `source_feed` and `ingested_at` as parameters | Read the clock or the file itself inside the function | Same input gives same output: easy to test and to replay from old raw files with their original ingest time | The caller must pass two extra arguments |
| 34 | 2026-11-15 | One `ingested_at` per run, used for every raw file name and stored on every row | Take the time separately inside each step | A row can be traced to the exact raw file it came from; the three feeds of one run share one timestamp | Raw file names of one run no longer differ by a second; two runs inside the same second would collide (mode `"x"` makes that loud) |
| 35 | 2026-11-15 | `main` lands all feeds first, then validates and transforms | Process each feed fully inside the fetch loop | A bug or a BMKG structure change in processing can never stop the run before the remaining feeds are fetched and saved (BMKG keeps no history) | Slightly longer loop structure; processing starts only after all fetches finish |
| 36 | 2026-11-15 | Rejected records are logged with their reasons (WARNING) for now, and do not change the exit code | Stop the run; write them to a quarantine file now | The raw file still holds every record, so nothing is lost; rejects are a data-quality signal, not a failed run | Rejects are easy to miss in a log until a quarantine table exists (comes with `load.py`) |
